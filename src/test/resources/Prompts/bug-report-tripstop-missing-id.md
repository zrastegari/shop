یک مشکل طراحی واقعی در تست دستی B5 پیدا کردیم که باید فیکس بشه.

## مشکل

Endpoint زیر (طبق پرامپت اصلی فاز ۲) قراره یک توقف مشخص رو کامل علامت بزنه:
```
POST /api/sharedtaxi/active-trips/{id}/stops/{stopId}/complete
```

اما وقتی `GET /api/sharedtaxi/active-trips/{id}` رو زدم، هر آیتم داخل آرایه‌ی `stops`
فقط این فیلدها رو داره:
```json
{
  "passengerId": 21,
  "type": "PICKUP",
  "lat": 35.715,
  "lng": 51.406,
  "sequenceOrder": 1,
  "completed": false
}
```

**هیچ فیلد `id` یا `stopId` جداگانه‌ای وجود نداره.** یعنی از سمت کلاینت (یا حتی از
سمت هر کد دیگه‌ای که بخواد این endpoint رو صدا بزنه)، امکان نداره بفهمیم `{stopId}`
باید چی باشه — چون هیچ شناسه‌ای برای ارجاع به یک توقف خاص در دسترس نیست.

## چرا این اتفاق افتاد (حدس، نه قطعی)

`TripStop` به‌عنوان یک کلاس **embedded** (نه Document جدا با `@Id` خودش) طراحی شده
بود — طبق پرامپت اصلی، این عمدی بود (چون توقف‌ها زیرمجموعه‌ی سند `ActiveSharedTrip`
هستن، نه یک collection جدا). ولی این باعث شده که MongoDB به‌صورت خودکار به هر
`TripStop` یک `_id`ی جدا نده (بر خلاف Document های اصلی که MongoDB خودکار
`ObjectId` بهشون می‌ده).

## راه‌حل

یک فیلد `id` (از نوع String، مثلاً با `UUID.randomUUID().toString()` تولید بشه در
لحظه‌ی ساخته شدن هر `TripStop`، چه در حین enumeration مرحله ۲، چه هر جای دیگه که
`TripStop` جدید می‌سازیم) به کلاس `TripStop` اضافه کن. این شناسه باید:

1. در لحظه‌ی ساخت `TripStop` تولید بشه (نه بعداً)
2. در پاسخ JSON (چه `GET active-trips/{id}`، چه در `proposedStops` داخل
   `SharedTaxiOffer`) نمایش داده بشه
3. وقتی یک offer قبول می‌شه (`accept`) و `proposedStops` جایگزین `stops` سفر فعال
   می‌شه، شناسه‌ها باید حفظ بشن (یا حداقل، توقف‌های از‌پیش‌موجود که فقط "insert" شدن،
   شناسه‌ی قبلی‌شون رو نگه دارن — این برای اینه که اگه یک توقف قبلاً `completed=true`
   بوده، بعد از یک offer جدید هم قابل شناسایی بمونه)
4. Endpoint تکمیل توقف (`POST .../stops/{stopId}/complete`) باید بر اساس همین `id`
   جدید، توقف مربوطه رو پیدا و `completed=true` کنه — نه بر اساس ترکیب
   `passengerId`+`type` (که هرچند در این سناریوی خاص یکتاست، ولی به‌طور کلی نمی‌تونیم
   مطمئن باشیم همیشه یکتا می‌مونه، مخصوصاً اگه یک مسافر به هر دلیلی دو بار در لیست
   ظاهر بشه یا سناریوهای لبه‌ای دیگه).

## تست

لطفاً یک تست unit جدید (یا موجود رو گسترش بده) اضافه کن که تایید کنه:
- هر `TripStop` جدید یک `id` غیرخالی و یکتا داره
- `id` بعد از یک عملیات `accept` (که `proposedStops` رو جایگزین `stops` می‌کنه)
  حفظ می‌مونه برای توقف‌هایی که از قبل وجود داشتن

## بعد از این تغییر

لطفاً کامپایل و کل تست‌ها رو دوباره اجرا کن (چون `TripStop` توی چند جای دیگه هم
استفاده می‌شه — enumeration، offer، و غیره — این تغییر ممکنه چند تا فایل رو تحت تاثیر
قرار بده). بعد از تایید سبز بودن، من دوباره B5 (تکمیل توقف) رو با `stopId` واقعی
تست می‌کنم.
