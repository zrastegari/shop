یک باگ واقعی در تست یکپارچگی پیدا کردیم که باید بررسی بشه. جزئیات کامل:

## سناریو

دو `POST /api/carpool/trips` زدم (پورت 9090):
- سفر اول: `userId=1`, `tripType=IN_CITY`, origin=(35.6997, 51.3380), dest=(35.7219, 51.3347)
- سفر دوم: `userId=2`, `tripType=IN_CITY`, origin=(35.7005, 51.3390), dest=(35.7225, 51.3355) —
  عمداً خیلی نزدیک سفر اول (چند صد متر فاصله) و بازه‌ی زمانی هم‌پوشان

**نتیجه‌ی مورد انتظار:** پاسخ سفر دوم باید حداقل یک match به سفر اول نشون بده.
**نتیجه‌ی واقعی:** `"matches": []` — خالی.

`carpool.matching.use-distance-matrix-api=true` هست و کلید Neshan هم در
`application.properties` (`neshan.api-key`) تنظیم و معتبره.

## لاگ‌هایی که در کنسول دیدیم

```
CarpoolTripService: سفر جدید ثبت شد: id=6a800702e3ee4615d6afbb7c, tripType=IN_CITY
CarpoolMatchingService: مرحله ۱: تعداد ۱ سفر کاندید پیدا شد برای ... با 6a800702e3ee4615d6afbb7c
...
CarpoolTripService: سفر جدید ثبت شد: id=6a800784e3ee4615d6afbb7d, tripType=IN_CITY
CarpoolMatchingService: مرحله ۱: تعداد ۲ سفر کاندید پیدا شد برای ... با 6a800784e3ee4615d6afbb7d
```

**نکته‌ی مهم:** بعد از این خط، **هیچ لاگ دیگه‌ای از `CarpoolMatchingService` دیده نمی‌شه** —
نه لاگی از فیلتر Haversine (مرحله ۲)، نه از فراخوانی Neshan Distance Matrix
(مرحله ۳)، نه از رد شدن یا قبول شدن match. الگوریتم به‌طور «خاموش» بعد از مرحله ۱
متوقف می‌شه یا نتیجه‌ش لاگ نمی‌شه.

همچنین یه چیز عجیب در متن لاگ: نوشته «برای tripType 6 با ...» — عدد `6` اینجا معنی
نداره چون `TripType` فقط `IN_CITY`/`OUT_CITY` داره. این می‌تونه یه مشکل در فرمت
پیام لاگ باشه (شاید جای پارامترها عوض شده، یا یه enum دیگه با اشتباه چاپ شده) —
لطفاً این خط لاگ رو هم پیدا کن و ببین منظورش چیه.

## چیزی که ازت می‌خوام

1. **اول:** سطح لاگ رو در `application.properties` موقتاً روی `DEBUG` برای پکیج
   `com.learning.shop` بذار (اگه از قبل نیست) تا هیچ لاگی گم نشه:
   ```properties
   logging.level.com.learning.shop=DEBUG
   ```
2. **کد `CarpoolMatchingService` رو بررسی کن** و مطمئن شو که:
   - بعد از فیلتر مرحله ۱ (که کاندیدا پیدا می‌کنه)، واقعاً حلقه‌ی مرحله ۲
     (Haversine) روی هر کاندیدا اجرا می‌شه
   - هر رد شدن (چه در Haversine، چه در فراخوانی Neshan) یک لاگ واضح تولید کنه —
     مثلاً «کاندیدا X رد شد در مرحله ۲: فاصله‌ی مبدأ Y متر > آستانه‌ی Z متر»
   - اگه فراخوانی Neshan API با خطا مواجه می‌شه (مثلاً timeout، پاسخ نامعتبر،
     exception)، اون خطا **باید لاگ بشه**، نه این‌که به‌آرومی قورت داده بشه و
     فقط match تولید نشه
3. **خط لاگ عجیب `tripType 6` رو پیدا کن** و توضیح بده چرا این عدد چاپ شده —
   ممکنه یه اشتباه در فرمت‌بندی پیام لاگ (`String.format` یا مشابه) باشه.
4. بعد از این تغییرات، برنامه رو دوباره اجرا کن و دقیقاً همین دو request
   (userId=1 و userId=2 با مختصات بالا) رو دوباره بزن، و لاگ کامل خروجی رو برام
   بفرست تا با هم ببینیم دقیقاً کجا و چرا match رد می‌شه.

فعلاً حدس نزن که مشکل از Neshan API خارجیه — ممکنه باشه، ولی چون لاگ‌های مرحله ۲ و ۳
اصلاً چاپ نمی‌شن، اول باید مطمئن بشیم خود کد داره درست اون مراحل رو اجرا و لاگ
می‌کنه.
